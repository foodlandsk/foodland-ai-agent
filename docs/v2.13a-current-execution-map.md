## Kľúčové zistenie: internal execution unification je už z 90 % hotová

Zadanie predpokladalo, že treba vybudovať jednotný interný execution
boundary od nuly. Realita: **`app.main._chat_internal()` už dnes je
takmer presne to, čo V2.13a žiada od `AdvisorEngine`** — jediný
zjednotený exit point, execution-context-aware, s jedným miestom pre
`SearchQualityTrace` emission (V2.12.4). `chat()` (HTTP route) je už
dnes tenký adaptér:

```python
def chat(chat_request: ChatRequest, request: Request) -> dict:
    return _chat_internal(chat_request, request)
```

Čo skutočne chýba: **pomenovaná, formálna hranica** (`AdvisorEngine`
trieda/modul) a **odstránenie potreby duck-typed `_FakeRequest` shim
pre interných volajúcich** — dnes 4 rôzne miesta v repozitári nezávisle
konštruujú svoj vlastný `_FakeRequest`, namiesto volania jedného
zdieľaného API.

## `app.workflow_registry.select_workflow()` — shadow label, NIE router

Overené priamym čítaním (`app/workflow_registry.py`, V2.7): toto je
**čistá funkcia nad UŽ VYPOČÍTANÝMI signálmi** (`RoutingSignals`
dataclass — jedno pole na každú vetvu, ktorú `chat()` kaskáda už
kontroluje, presne v tom istom poradí). `select_workflow()` NIKDY
nevolá žiadny detektor sama, len vracia `WorkflowSelection(workflow_id,
confidence, reason)` — čisto na účely `response["workflow_id"]`/
`workflow_confidence` polí (telemetria/observability), **nikdy neriadi,
KTORÁ vetva `_chat_impl()` sa spustí**. Toto potvrdzuje presne to, čo
`docs/routing-debt.md` opisuje: `related_subject` vetva vždy vracia
`LEGACY_FALLBACK` label (riadok 305-306), pretože `related_products`
nemá VLASTNÝ `WorkflowContract` v `WORKFLOWS` registri vôbec — len
`USE_CASE_ADVICE`/`COMPARISON`/`REPLACEMENT`/`FAQ_INFORMATIONAL` sú
`SHADOW` (rozpoznané, ale nepreklopené), `PRODUCT_LOOKUP`/
`CATEGORY_BROWSE`/`ATTRIBUTE_SEARCH`/`RECIPE_SHOPPING` sú `MIGRATED`
(skutočne bežia cez V2.4-V2.8 pipeline), zvyšok je `LEGACY`.

## `request` parameter — presné použitie vnútri `_chat_impl()`

Overené `grep`-om na presné slovo `request` (nie `chat_request`): **len
2 funkčné miesta** v celej ~1160-riadkovej `_chat_impl()`:

1. `isinstance(request, Request)` — fallback rezolúcia execution_context,
   relevantná LEN keď `execution_context is None`.
2. `client_key = get_client_key(request)` — `request.headers.get("x-forwarded-for")`
   alebo `request.client.host`.

Toto potvrdzuje, že `_chat_impl()`/`_chat_internal()` sú už takmer
plne odviazané od skutočnej FastAPI `Request` sémantiky — potrebujú len
jednu odvodenú hodnotu (`client_key: str`), nie celý objekt.

## Záver pre návrh AdvisorEngine (V2.13a Phase 4)

Vzhľadom na vyššie: `AdvisorEngine.run()` môže byť tenký, bezpečný
wrapper okolo NEZMENENÉHO `_chat_internal()`/`_chat_impl()` — nemusí (a
nemá) kopírovať žiadnu logiku. Interne poskytne rovnaký `_FakeRequest`-tvarový
shim (teraz na JEDNOM mieste, `app/advisor_engine.py`), zostavený z
`AdvisorRequest.client_key`, takže `get_client_key()`/`isinstance()`
logika vnútri `_chat_impl()` zostáva úplne nezmenená — nulové riziko
pre existujúcich ~40 test call sites, ktoré priamo volajú
`chat()`/`_chat_internal()`/`_chat_impl()`.
